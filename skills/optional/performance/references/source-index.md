# Performance source index

Use this index to select evidence for the current workload. These sources define methods and tool behavior; they do not supply universal latency targets, sample sizes, utilization ceilings, or cost limits. Those must come from the product's performance contract and the measured environment.

## Core measurement, SLOs, and overload

- [Google SRE: Monitoring Distributed Systems](https://sre.google/sre-book/monitoring-distributed-systems/) — the four golden signals: latency, traffic, errors, and saturation; distinguish successful and failed latency; use workload-specific demand and constrained-resource signals; treat rising tail latency as an early saturation indicator.
- [Google SRE: Service Level Objectives](https://sre.google/sre-book/service-level-objectives/) — define SLIs/SLOs from user behavior; latency, error rate, throughput, and correctness are distinct concerns; specify measurement windows and conditions; distributions and tail percentiles matter more than averages alone; heterogeneous workloads may need separate objectives; error budgets are preferable to an unrealistic universal 100% target.
- [Google SRE: Practical Alerting from Time-Series Data](https://sre.google/sre-book/practical-alerting/) — retain high-level objective signals while preserving component granularity for diagnosis; use alerting that can expose latency-tail contributors rather than only aggregate averages.
- [Google SRE: Handling Overload](https://sre.google/sre-book/handling-overload/) — distinguish a small overloaded subset from broad backend overload; bound and reason about retries; allow errors to propagate instead of amplifying overload when the backend is broadly saturated.
- [Google SRE: Addressing Cascading Failures](https://sre.google/sre-book/addressing-cascading-failures/) — load-test capacity limits and overload failure modes; use degradation, early rejection, load shedding, and capacity planning to contain saturation and cascading failure.
- [Google SRE: Production Services Best Practices](https://sre.google/sre-book/service-best-practices/) — measure user-relevant performance; use load testing rather than historical resource/QPS assumptions; plan for outage headroom; test behavior beyond rated capacity and verify graceful degradation.

## Resource diagnosis, Linux perf, and profiling

- [Brendan Gregg: The USE Method](https://www.brendangregg.com/usemethod.html) — for every resource, check utilization, saturation, and errors; defines saturation as extra work that cannot be serviced, commonly queueing; warns that long-window averages hide burst saturation; applies to software limits and cloud cgroup/tenant controls as well as hardware.
- [Brendan Gregg: Linux perf Examples](https://www.brendangregg.com/perf.html) — event-oriented Linux `perf` investigations for on-CPU paths, cache misses, memory stalls, allocations, TCP retransmits, kernel/user tracing, JIT symbols, and stack traces. Use the relevant example rather than treating a tool list as a diagnosis.
- [Brendan Gregg: CPU Flame Graphs](https://www.brendangregg.com/FlameGraphs/cpuflamegraphs.html) — sampled stack traces visualize where CPU samples accumulate; documents `perf record`/`perf script` workflows and their CPU, filesystem, disk, and stack-unwinding overhead; a flame graph describes sampled activity, not wall-clock wait or causality by itself.
- [Linux `perf_event_open(2)`](https://man7.org/linux/man-pages/man2/perf_event_open.2.html) — authoritative system-call reference for Linux performance events and the permissions/configuration boundary behind `perf`; use when kernel, counter, or access semantics matter.
- [Linux kernel: Discovering workload subsystems](https://www.kernel.org/doc/html/latest/admin-guide/workload-tracing.html) — kernel-maintained guide showing how `perf` and tracing expose workload resource use, how `perf stat` reports hardware/software events, and why matching the `perf` build to the kernel matters; exact events depend on the current system.

## Runtime-specific measurement and profiling

- [Oracle Java Flight Recorder configurations](https://docs.oracle.com/en/java/javase/21/jfapi/flight-recorder-configurations.html) — `default.jfc` is intended for continuous low-overhead recording (typically under 1% in the documented configuration); `profile.jfc` records more events and can impose more overhead. Keep configuration and JDK version in the evidence.
- [Oracle Java diagnostic tools](https://docs.oracle.com/en/java/javase/17/troubleshoot/diagnostic-tools.html) — JFR records timestamped JVM/application events and is suited to latency, GC, allocation, synchronization, and other runtime investigations; continuous and profiling configurations have different overhead.
- [Go diagnostics](https://go.dev/doc/diagnostics) — `pprof` supports CPU, heap, blocking, and other profiles; production profiling is possible but adds cost, which should be measured; profiling modes can interfere with one another, so collect incompatible profiles separately.
- [Go `runtime/pprof` package](https://pkg.go.dev/runtime/pprof) — standard profile format and benchmark flags for CPU and memory profiles; use with `go test` or runtime endpoints as appropriate.
- [Go profile-guided optimization](https://go.dev/doc/pgo) — production profiles are preferred when representative; microbenchmarks are usually poor PGO inputs because they exercise too little of the application. Do not generalize a microbenchmark win to whole-program behavior.
- [Node.js performance measurement APIs](https://nodejs.org/api/perf_hooks.html) — high-resolution time, user/resource timing, function timing, HTTP/network/DNS timing, histograms, event-loop utilization, and event-loop delay; record the Node version and account for asynchronous measurement semantics.
- [Python debugging and profiling](https://docs.python.org/3/library/debug.html) — official routing for `cProfile`, deterministic profiling limitations, `timeit`, tracing, and `tracemalloc`; choose the tool according to CPU, timing, execution, or allocation question.
- [Python `timeit`](https://docs.python.org/3/library/timeit.html) — suitable for small snippets; setup is excluded, garbage collection is disabled by default during timing, and repeated results can be dominated by interference. Re-enable relevant behavior and use a representative workload for application claims.
- [.NET diagnostics overview](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/) — routes between counters, distributed traces, dumps, and profiling tools; distributed traces localize work across processes and can be sampled to bound overhead.
- [.NET `dotnet-counters`](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/dotnet-counters) — first-level runtime/process metrics including CPU, working set, GC, allocation, lock contention, and thread-pool queue; useful for confirming a resource hypothesis, not a replacement for request-level latency evidence.
- [.NET EventPipe](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/eventpipe) — `dotnet-trace` and EventPipe collect runtime/application traces for performance analysis; exact providers and overhead depend on runtime version and configuration.

## Benchmark and test validity

- [Go `testing` benchmarks](https://pkg.go.dev/testing) — benchmark timing is managed by the framework; setup can be outside the timed loop; use the benchmark contract correctly and report custom units explicitly. The current documentation also explains how the loop protects calls/results from compiler elimination.
- [Google SRE: SLO measurement conditions](https://sre.google/sre-book/service-level-objectives/) — an SLO must specify the metric, aggregation/window, and conditions under which it is valid; burst load and tail behavior can be hidden by broad averages.
- [AWS Well-Architected: Load test your workload](https://docs.aws.amazon.com/wellarchitected/latest/performance-efficiency-pillar/perf_process_culture_load_test.html) — use realistic load and production-like infrastructure; use synthetic or sanitized data; define objectives/scenarios/duration/users; monitor all resources; test nonlinear scaling and iterate after changes. AWS-specific policy and service limits still apply.
- [Azure Well-Architected: Architecture strategies for performance testing](https://learn.microsoft.com/en-us/azure/well-architected/performance-efficiency/performance-test) — use measurable goals, production-like conditions, representative data characteristics, continuous and hypothesis-driven testing, and multiple test types; performance targets and thresholds are workload-specific.

## Capacity, elasticity, and cloud cost boundaries

- [AWS Performance Efficiency Pillar](https://docs.aws.amazon.com/wellarchitected/latest/performance-efficiency-pillar/welcome.html) — performance efficiency is an ongoing process of choosing resources, monitoring, testing, and adapting; use only for AWS-scoped decisions and verify current service behavior.
- [AWS PERF02-BP05: Scale compute resources dynamically](https://docs.aws.amazon.com/wellarchitected/latest/performance-efficiency-pillar/perf_compute_hardware_scale_compute_resources_dynamically.html) — test elasticity and scale transitions; choose a scaling metric that reflects the workload (for example, queue depth rather than CPU for a queue-bound workload); scale up and down safely.
- [Google Cloud Well-Architected: Performance optimization](https://docs.cloud.google.com/architecture/framework/performance-optimization) — define granular requirements, plan resource allocation, monitor with logs/traces/metrics, and continuously optimize; explicitly frames performance versus cost as a trade-off rather than a universal minimization goal.
- [Google Cloud Well-Architected: Take advantage of elasticity](https://docs.cloud.google.com/architecture/framework/performance-optimization/elasticity) — determine capacity at baseline, choose scaling responses for increased/decreased demand, and use workload-appropriate metrics such as latency, serving capacity, CPU, or custom signals.
- [Azure Well-Architected: Performance efficiency quick links](https://learn.microsoft.com/en-us/azure/well-architected/performance-efficiency/) — routes to measurable targets, capacity planning, performance data, load testing, scaling/partitioning, and continuous optimization.
- [Azure Well-Architected: Monitoring workload reliability](https://learn.microsoft.com/en-us/azure/well-architected/reliability/monitoring) — define finite per-stamp capacity limits, monitor saturation before reliability is affected, and determine practical capacity through load testing, observation, and iterative tuning rather than assuming platform limits are the full model.

## Source and applicability limits

- Google SRE and Brendan Gregg provide general methods, not a guarantee that every workload is CPU/resource-bound or that a particular percentile/threshold is correct.
- Runtime documentation describes instrumentation semantics and overhead for a versioned runtime; it does not prove that a profile is representative of production.
- Cloud Well-Architected guidance is provider-specific where it names services, quotas, policies, or scaling mechanisms. Do not transfer AWS, Google Cloud, or Azure limits across providers.
- A benchmark result is evidence only for its measured workload, data, environment, software versions, configuration, metric definition, and observation method. Extrapolation to production capacity requires a validated model and representative load test.
